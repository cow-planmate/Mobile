# Project Rules

## 1. 코드 작성 규칙

- 간결하고 효율적인 코드를 작성합니다.
- 수정 내역별 개별 주석 남기기 등 난잡한 주석 작성을 지양하고 코드 가독성을 유지합니다.
- 기존 코드베이스의 컨벤션(camelCase, snake_case 등)을 준수하여 프로젝트의 일관성을 유지합니다.

## 1. 자율적 사고 및 능동적 해결

- 사용자가 요구 사항을 전달하면 스스로 깊이 생각하고 능동적으로 답을 찾아 작업을 진행합니다.
- 한 번에 끝내는 것에 그치지 않고, 수정 과정 중간중간 계속 스스로 생각하고 점검하며 완성도 있게 다듬어 나갑니다.
- 형식적인 사전 승인 절차나 경직된 보고 단계에 얽매이지 않고 실질적인 코드 수정과 개선을 즉시 실행합니다.

## 2. 응답 및 문서 작성 규칙

- 핵심 내용 중심의 필요한 문장으로만 구성합니다.
- 이모티콘 및 과도한 특수기호 사용을 배제합니다.
- 보고서 형식의 정돈된 구조를 유지하여 작성합니다.
- 사용자에게 역으로 질문하는 행위를 금지하며, 확인이나 선택을 요구하는 문장을 구성하지 않습니다.

## 2. 쉽고 직관적인 설명

- 난해한 전문 용어나 복잡한 기술 용어의 나열을 지양하고, 누구나 한눈에 쉽게 이해할 수 있도록 일상적이고 명확한 언어로 설명합니다.
- 문제점, 원인, 해결 방향을 설명할 때는 직관적인 표현과 쉬운 비유를 우선 활용합니다.

## 3. 작업 수행 범위 및 절차 규칙

- 정보 제공, 확인, 원인 분석 요청 시 코드 수정, 파일 편집, 파일 작성을 일체 수행하지 않습니다.
- 코드 수정 시 '1. 분석 보고서 및 수정 제안' -> '2. 사용자의 명시적 승인/지시' -> '3. 코드 수정 및 테스트' 3단계 절차를 필수로 거칩니다.
- 사용자가 명시적으로 요청한 사항 이외의 임의 작업, 선제적 리팩토링, 예방적 코드 수정을 일체 금지합니다.
- 사용자가 설정하거나 수정한 파일, 설정값, 워킹 트리 변경 사항을 임의로 되돌리거나(`git checkout`, `git restore` 등) 덮어쓰는 행위를 일체 금지하며, 오직 요청받아 수정한 범위만 엄격히 다룹니다.

## 4. 테스트 및 예외 처리 규칙

- 작성 및 수정되는 코드에 대해 예외 처리 기준과 테스트 코드 작성 여부를 사전에 명시하고 테스트를 반드시 실행합니다.
- 오류 발생 시 원인 분석을 우선 수행하고 해결 방안의 순서를 제시한 후 디버깅을 진행합니다.

## 5. 변경점 관리 규칙

- 승인 후 코드를 수정할 때에는 전체 코드 재출력을 지양하고 변경된 부분만 간략히 요약하여 제시합니다.

## 6. 성능 및 리소스 관리 규칙

- 대용량 데이터 처리 시 시간 및 공간 복잡도를 고려하여 효율적인 자료구조와 알고리즘을 선택합니다.
- 루프 내부의 무거운 연산이나 중복 호출을 최적화하여 불필요한 연산을 제거합니다.

## 7. 백엔드 연계 및 로직 교차 검증 규칙

- 모든 기능 구현, 로직 분석 및 문제 해결 시 항상 백엔드(`Backend-v2`) 소스 코드(Controller, DTO, Entity, Service, WebSocket STOMP 등)와 앱(`App/Mobile`) 소스 코드를 1:1로 교차 점검하여 불일치 여부를 전수 탐지하고 원인을 파악하여 해결합니다.

## 8. 커밋 메시지 규칙

- 커밋 메시지는 `type: <내용 요약>` 형태의 제목과 변경된 핵심 내용을 불릿으로 정리한 상세 본문(Body)으로 구성합니다.
- 타입 접두사: `feat:`, `fix:`, `refactor:`, `style:`, `test:`, `docs:`
- 본문에는 주요 변경 사항을 영역별로 명확하고 간결하게 요약하여 작성합니다.

## 3. 코드 품질 및 안정성 유지

- 간결하고 효율적인 코드를 작성하며, 기존 코드베이스의 컨벤션을 준수합니다.
- 작업 후 타입 검사 및 테스트를 실행하여 정상 작동 여부를 검증합니다.

## 에이전트 분담 및 사용량 관리

- 사용자는 작업별 서브 에이전트 활용을 승인했다. 짧은 질문과 단순 수정은 주 에이전트가 직접 처리하며, 독립적인 작업만 위임한다.
- 시안, 스크린샷 비교, 시각적 UI 평가와 멀티모달 검토는 Antigravity를 우선 사용한다. 기본 모델은 `gemini-3.8-flash-low`; 여러 화면의 일관성·복잡한 상호작용을 판단하거나 Low 결과가 불충분한 경우 `gemini-3.8-flash-high`를 사용한다. Pro는 사용하지 않는다. 이미지 생성 지원은 별도로 확인하며, 텍스트 검토 성공을 이미지 생성 성공으로 보고하지 않는다.
- 파일 탐색·좁은 범위의 사실 확인은 Codex `gpt-5.6-luna` / low 서브 에이전트에 맡긴다. 새 에이전트에는 전체 대화 대신 목표, 관련 경로, 제한, 결과 형식만 전달한다.
- 로직·원인 분석·변경안 검토는 Claude `sonnet` / low를 사용한다. 단순 텍스트 요약은 `haiku`를 사용할 수 있다. 전체 통합, 실제 코드 수정, 테스트와 최종 판단은 주 에이전트가 담당한다.
- Claude `opus`는 앱·백엔드·실시간 동기화에 걸친 복합 원인 분석, 동시성·데이터 무결성·인증 권한처럼 판단 오류의 영향이 큰 변경안 검토, 또는 Sonnet이 근거를 확인한 뒤에도 해결하지 못한 쟁점에 사용한다. 해당 조건이면 주 에이전트가 사용 이유를 밝히고 필요한 범위만 1회 위임한다. 단순 탐색·요약·일반 UI 작업이나 전체 작업의 중복 검토에는 사용하지 않는다. 호출은 `python scripts/delegate.py claude --model opus --prompt "쟁점과 관련 파일 경로"`로 하며, 기존 시간·비용 제한을 유지한다.
- 외부 모델은 `python scripts/delegate.py claude --prompt "작업과 명시적 파일 경로"` 또는 `python scripts/delegate.py antigravity --prompt "작업과 명시적 이미지 경로"`로 호출한다. 필요하면 `--model`을 지정한다. 현재 연결은 읽기 전용 자문용이며, 기존 승인·수정 범위를 외부 도구에 확대하지 않는다.
- Antigravity의 plan 모드는 운영 모드이지 파일 접근 보안 경계가 아니다. 수정 권한을 우회하는 옵션은 사용하지 않고, 결과와 작업 트리를 검증한다.
- 화면·기능별로 묶어 호출하고 동일 작업을 여러 모델에 중복 전달하지 않는다. 기본 동시 위임은 최대 2개, 답변은 250단어 이내로 제한한다. 위 조건에 따른 선별 사용 외에 제한 없는 재시도나 호출 실패만을 이유로 한 자동 상위 모델 전환은 하지 않는다.
- 반환 JSON의 사용량을 확인한다. 모델 분담은 주 모델 사용량을 줄일 수 있지만 전체 토큰이나 구독 사용량 감소를 보장하지 않는다.
- 실행 실패·시간 초과·이미지 접근 불가를 성공으로 보고하지 않는다. 대체 도구를 사용한다면 변경 이유와 실제 사용 도구를 알린다. 외부 모델 답변은 근거를 검증한 후 반영한다.
