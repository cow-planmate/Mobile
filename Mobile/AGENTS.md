# Project Rules

## 1. 코드 작성 규칙

- 간결하고 효율적인 코드를 작성합니다.
- 수정 내역별 개별 주석 남기기 등 난잡한 주석 작성을 지양하고 코드 가독성을 유지합니다.
- 기존 코드베이스의 컨벤션(camelCase, snake_case 등)을 준수하여 프로젝트의 일관성을 유지합니다.

## 1. 자율적 사고 및 능동적 해결

- 사용자가 요구 사항을 전달하면 스스로 깊이 생각하고 능동적으로 답을 찾아 작업을 진행합니다.
- 한 번에 끝내는 것에 그치지 않고, 수정 과정 중간중간 계속 스스로 생각하고 점검하며 완성도 있게 다듬어 나갑니다.
- 형식적인 사전 승인 절차나 경직된 보고 단계에 얽매이지 않고 실질적인 코드 수정과 개선을 즉시 실행합니다.

## 2. 응답 및 문서 작성 규칙

- 핵심 내용 중심의 필요한 문장으로만 구성합니다.
- 이모티콘 및 과도한 특수기호 사용을 배제합니다.
- 보고서 형식의 정돈된 구조를 유지하여 작성합니다.
- 사용자에게 역으로 질문하는 행위를 금지하며, 확인이나 선택을 요구하는 문장을 구성하지 않습니다.

## 2. 쉽고 직관적인 설명

- 난해한 전문 용어나 복잡한 기술 용어의 나열을 지양하고, 누구나 한눈에 쉽게 이해할 수 있도록 일상적이고 명확한 언어로 설명합니다.
- 문제점, 원인, 해결 방향을 설명할 때는 직관적인 표현과 쉬운 비유를 우선 활용합니다.

## 3. 작업 수행 범위 및 절차 규칙

- 정보 제공, 확인, 원인 분석 요청 시 코드 수정, 파일 편집, 파일 작성을 일체 수행하지 않습니다.
- 코드 수정 시 '1. 분석 보고서 및 수정 제안' -> '2. 사용자의 명시적 승인/지시' -> '3. 코드 수정 및 테스트' 3단계 절차를 필수로 거칩니다.
- 사용자가 명시적으로 요청한 사항 이외의 임의 작업, 선제적 리팩토링, 예방적 코드 수정을 일체 금지합니다.
- 사용자가 설정하거나 수정한 파일, 설정값, 워킹 트리 변경 사항을 임의로 되돌리거나(`git checkout`, `git restore` 등) 덮어쓰는 행위를 일체 금지하며, 오직 요청받아 수정한 범위만 엄격히 다룹니다.

## 4. 테스트 및 예외 처리 규칙

- 작성 및 수정되는 코드에 대해 예외 처리 기준과 테스트 코드 작성 여부를 사전에 명시하고 테스트를 반드시 실행합니다.
- 오류 발생 시 원인 분석을 우선 수행하고 해결 방안의 순서를 제시한 후 디버깅을 진행합니다.

## 5. 변경점 관리 규칙

- 승인 후 코드를 수정할 때에는 전체 코드 재출력을 지양하고 변경된 부분만 간략히 요약하여 제시합니다.

## 6. 성능 및 리소스 관리 규칙

- 대용량 데이터 처리 시 시간 및 공간 복잡도를 고려하여 효율적인 자료구조와 알고리즘을 선택합니다.
- 루프 내부의 무거운 연산이나 중복 호출을 최적화하여 불필요한 연산을 제거합니다.

## 7. 백엔드 연계 및 로직 교차 검증 규칙

- 모든 기능 구현, 로직 분석 및 문제 해결 시 항상 백엔드(`Backend-v2`) 소스 코드(Controller, DTO, Entity, Service, WebSocket STOMP 등)와 앱(`App/Mobile`) 소스 코드를 1:1로 교차 점검하여 불일치 여부를 전수 탐지하고 원인을 파악하여 해결합니다.

## 8. 커밋 메시지 규칙

- 커밋 메시지는 `type: <내용 요약>` 형태의 제목과 변경된 핵심 내용을 불릿으로 정리한 상세 본문(Body)으로 구성합니다.
- 타입 접두사: `feat:`, `fix:`, `refactor:`, `style:`, `test:`, `docs:`
- 본문에는 주요 변경 사항을 영역별로 명확하고 간결하게 요약하여 작성합니다.

## 3. 코드 품질 및 안정성 유지

- 간결하고 효율적인 코드를 작성하며, 기존 코드베이스의 컨벤션을 준수합니다.
- 작업 후 타입 검사 및 테스트를 실행하여 정상 작동 여부를 검증합니다.
