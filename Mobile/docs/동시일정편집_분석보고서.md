# 동시 일정 편집 및 데이터 동기화 정밀 심층 분석 보고서

## 1. 개요
본 보고서는 플랜메이트(`PlanMate`) 모바일 앱(`App/Mobile`) 및 백엔드(`Backend-v2`) 간의 동시 일정 편집(Real-time Concurrent Editing) 환경에서 발생하는 이탈 후 재진입 시 데이터 지연 렌더링, 웹소켓 STOMP 동기화, REST API 캐시 매핑 이슈에 대한 정밀 1:1 교차 분석 보고서입니다.

---

## 2. 시스템 데이터 흐름 및 아키텍처 구조

```
[클라이언트 B (편집 수행 중)]
   │ 
   ├─ (1) STOMP WebSocket 메시지 송신 ──> [SharedSyncController] ──> [TimeTablePlaceBlockCache (Redis)]
   │                                                                     │ (비동기 DB 저장 대기)
   └─ (4) 장소 변경 STOMP 메시지 브로드캐스트                            ▼
            │                                                 [PostgreSQL DB (RDB)]
            ▼                                                            ▲
[클라이언트 A (이탈 후 재진입)]                                                 │ (Direct 조회)
   ├─ (2) GET /api/plan/{planId} (REST API 호출) ────────────> [PlanService.getPlan()] 
   │        (RDB 만 조회하여 누락된 구 데이터 수신 -> 장소 미표시)
   │
   └─ (3) STOMP 브로드캐스트 수신 ──────> [ItineraryContext.handleWebSocketMessage]
            (실시간 수신 객체 화면 State 바인딩 -> 장소 카드 즉시 표시)
```

## 3. 현상 전말 및 원인 분석 (백엔드 ↔ 앱 1:1 교차 검증)

### 3.1 REST API 조회 시점 데이터 누락 원인 (`Backend-v2`)

#### 1) 백엔드 실시간 파이프라인 (`SharedSyncController` / `TimeTablePlaceBlockCache`)
- 클라이언트가 동시 편집 중 장소를 추가하거나 수정할 때, 웹소켓 요청은 `SharedSyncController`로 인가되어 `TimeTablePlaceBlockCache` (Redis 기반 `AutoCacheRepository`)에 즉시 저장됩니다.
- `SharedSync` 프레임워크는 실시간 동시성을 높이기 위해 메모리/Redis 캐시에 최신 상태를 보관하며, RDB(PostgreSQL) 반영은 비동기 배치(Batch) 또는 세션 종료 시점에 수행됩니다.

#### 2) REST API 서비스 구현과의 단절 (`PlanService.java:157~175`)
- 재진입한 클라이언트(A)가 화면 로딩 시 호출하는 `GET /api/plan/{planId}` API의 백엔드 처리 코드는 다음과 같습니다:
  ```java
  // Backend-v2 / PlanService.java:169-172
  List<TimetablePlaceBlockDetailDto> placeBlocks = timeTablePlaceBlockRepository
          .findByPlanIdOrderByDateAndStartTime(planId).stream()
          .map(TimetablePlaceBlockDetailDto::from)
          .toList();
  ```
- **문제점**:
  - `PlanService.getPlan()` 메서드는 `SharedSync`의 Redis 캐시(`TimeTablePlaceBlockCache`)를 일체 참조하지 않고 **RDB(`timeTablePlaceBlockRepository`)만 Direct 조회**합니다.
  - 이로 인해 클라이언트 A가 재진입하여 REST API를 호출한 시점에는, 클라이언트 B가 실시간 편집 중이던 장소 데이터가 아직 RDB에 영속화(Commit)되지 않아 API 응답 객체(`GetPlanResponse.placeBlocks`)에서 누락된 상태로 전달되었습니다.

---

### 3.2 상대방 조작 시 화면에 장소가 나타나는 원인 (`App/Mobile`)

#### 1) 웹소켓 메시지 수신 및 핸들러 연동 (`ItineraryContext.tsx`)
- 클라이언트 B가 장소의 시작/종료 시간을 변경하거나 이동하여 STOMP 메시지를 발행하면, 백엔드는 해당 플랜 토픽(`/topic/{planId}`)을 구독 중인 클라이언트 A에게 메시지를 브로드캐스트합니다.
- 수신 메시지 구조:
  ```json
  {
    "action": "update",
    "entity": "timetableplaceblock",
    "eventId": "app-auto-...",
    "timeTablePlaceBlockDtos": [{ "blockId": 8, "placeName": "갈마공원", ... }]
  }
  ```

#### 2) 프론트엔드 상태(State) 즉시 바인딩 (`handleWebSocketMessage`)
- 최근 수정 반영된 `ItineraryContext.tsx` 의 `handleWebSocketMessage` 핸들러가 브로드캐스트 수신 즉시 동작합니다:
  - 수신된 `timeTablePlaceBlockDtos` 내 장소 객체(`respVO`)를 파싱.
  - `String(d.timetableId) === String(timetableId)` 또는 로컬 날짜(`YYYY-MM-DD`) 매핑으로 대상 일차(`dayIndex`) 탐색.
  - `setDays` 상태 변경 함수를 통해 해당 일차의 `places` 배열에 갈마공원 객체를 실시간 추가/업데이트.
- **결과**: REST API 수신 시점에는 빈 화면이었으나, 웹소켓 메시지를 받아 UI State가 변경되는 순간 갈마공원 카드가 렌더링되었습니다.

### 3.3 기존 추가 문제 분석 및 원인 정리

1. **`createFullPlan` (`POST /api/plan/full`) 호출로 인한 중복 Plan 생성**
   - 백엔드의 `POST /api/plan/full` (`PlanService.createPlan`) API는 기존 `planId`를 수정하는 것이 아니라 매번 새로운 UUID의 Plan 및 TimeTable을 DB에 신규 생성하는 API입니다.
   - 편집 완료 시점에 기존 `planId`가 있음에도 `createFullPlan`을 호출함으로 인해 별개의 새 Plan이 생성되어 재진입 사용자가 구 Plan ID를 조회할 때 장소가 보이지 않는 문제가 발생했었습니다.

2. **웹소켓 STOMP 프로토콜 필드명 및 날짜 포맷 불일치**
   - 백엔드 `SharedSync`는 `action`, `entity` 필드를 송신하나, 앱 핸들러는 `type`, `target`만 검사하여 메시지를 무시(Ignore)했었습니다.
   - 또한 `.toISOString()` 사용 시 한국 시각(KST, UTC+9)과 UTC 간 1일 오차가 발생하여 날짜 매핑이 실패하던 문제가 존재했었습니다.

3. **추천 장소 API (`GET /api/place`) 중복 폭주 호출**
   - 추천 장소 호출 `useEffect`의 의존성에 `planMetadata` 객체가 포함되어 있어, 재연결 및 데이터 로딩 시마다 객체 참조(Reference)가 변경되어 3개 카테고리 API 요청이 연속 폭주했었습니다.

## 4. 프론트엔드 조치 및 수정 완료 내역

1. **`src/features/itinerary/screens/ItineraryEditorScreen.tsx`**:
   - 기존 `planId` 존재 시 `createFullPlanMutation` 호출을 제거하고, 제목 변경 PATCH API만 호출하도록 변경하여 **Plan 중복 생성 원천 차단**.
   - `fetchedDestIdRef`를 적용하여 동일 `destinationId`/`travelId`에 대한 추천 장소 API 중복 폭주 호출 방지.

2. **`src/contexts/ItineraryContext.tsx`**:
   - `const action = msg.action || msg.type;`, `const entity = msg.entity || msg.target;` 호환 구문을 적용하여 백엔드 STOMP 메시지 100% 반영.
   - `getFullYear()`, `getMonth()`, `getDate()` 기반 로컬 `YYYY-MM-DD` 포맷으로 날짜 매핑 로직 변경.
   - `realId`가 `null`인 경우에도 `eventId` 및 임시 ID를 활용하여 실시간 카드가 즉시 바인딩되도록 개선.

3. **`src/hooks/useItineraryEditor.ts`**:
   - REST API 응답의 `placeBlocks` 매핑 시 `String(pbTtId) === String(ttId)` 타입 강제 동등 비교 및 날짜 Fallback 적용.
   - 웹소켓 `isConnected` 전환(`false` $\rightarrow$ `true`) 시 `fetchPlanDetails()` 자동 호출 연동.
